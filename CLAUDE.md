# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Go library for image generation via Gemini / Vertex AI, built on top of `github.com/shouni/go-gemini-client`. It adds what the raw client lacks: pluggable reference-image resolution (direct `gs://` reference, GCS/HTTP fetch, Gemini File API upload with cache-backed reuse), in-memory JPEG compression, request-level rate limiting / concurrency / timeouts, and unified single/multi reference-image generation. No main package.

## Commands

```sh
go build ./...
go vet ./...
go test -race ./...                              # CI runs tests with -race
go test ./generator/ -run TestGenerateAppliesRateLimit   # single test
test -z "$(gofmt -l .)"                          # CI fails on unformatted code
golangci-lint run                                # CI uses v2.12.2; config in .golangci.yml
```

## Architecture

Two public packages plus one internal, in a ports-and-adapters layout:

- **`ports/`** — interfaces and request/response types, plus `ExtensionByMIMEType` (the one helper that operates on them; see below). Consumers inject implementations of `ContentReader` (GCS-style `gs://` access), `Downloader` (HTTP fetch — SSRF protection / domain allow-listing is deliberately the caller's responsibility), `ImageCacher` (`Get`/`Set` only), and `ReferenceResolver` (how one reference becomes an attachment). `ImageGenerator` (one method: `Generate`) is the public entry interface — note consumers tend to redeclare it locally (go-comic-kit does, at `internal/operations/image_output.go`), which is idiomatic Go: only the *inbound* ports have to be defined here.
- **`generator/`** — one layer: `Generator` (`Generate`) plus the resolvers it delegates reference handling to. The old `GeminiImageCore` / `GeminiGenerator` split existed to isolate fetch/upload/compress; v1.14 moved those into resolvers, so the split lost its reason and collapsed. (`GenerateSingleImage`/`GenerateFusedImage` had already merged in v1.13: `Images` with one element is the old single, several is the old fusion, empty is text-only.)
- **`internal/imgutil/`** — stateless MIME detection/guessing and PNG/GIF→JPEG compression helpers. Still internal: consumers now need MIME→extension, but that is one function, re-exported through `ports.ExtensionByMIMEType` rather than by promoting the package (which would also expose the compression and sniffing helpers nobody asked for).

### Behavior that spans files (worth knowing before editing)

- **Reference resolution is injected, not decided by the kit** (`resolver.go`, `resolver_fileapi.go`). Three implementations: `GCSResolver` (`gs://` → direct URI reference, **zero dependencies**, Vertex-only), `FetchResolver` (fetch → MIME detect → optional compress → inline bytes, no backend constraint), `FileAPIResolver` (upload + cache + singleflight; honors a caller-supplied `FileAPIURI` by skipping the upload; Gemini-API-only). **Both backend constraints are enforced at construction** via the package-private `backendConstrained` interface: `New` returns `ErrVertexAIRequired` or `ErrGeminiAPIRequired` on a mismatch, but only when the client actually declares its backend — an undeclared client (test fake, non-forwarding wrapper) passes, because absence of evidence is not a mismatch. The `FileAPIResolver`-on-Vertex case is the one worth enforcing loudest: unguarded it still *works*, by failing every upload and falling through to inline, which costs a second download of every `gs://` reference and a warning per image while silently giving up the zero-transfer path. `ResolverChain` tries them in order. **Only `ports.ErrResolverNotApplicable` advances the chain** — a real error stops it, because letting a fetch failure fall through turns a network outage into "could not resolve the reference" and erases the cause. Nothing handled it → `ErrUnresolvedReference` (a misconfigured chain). Empty `ImageURI`s never reach a resolver; `collectImageAttachments` drops them.
- **A failed upload declines rather than errors.** `FileAPIResolver.Resolve` logs a warning and returns `ErrResolverNotApplicable` so the chain's next resolver (normally `FetchResolver`) takes over — the upload is a payload-size optimization, not a correctness requirement. **Exception: when the failure is the caller's own cancellation, the error propagates instead** — declining would refetch the same image only to die of the same cancellation (`TestFileAPIResolverCancelDoesNotDecline` pins this).
- **File API cache contract** (`resolver_fileapi.go`): `ensureUploaded` caches the uploaded URI (a plain string) under `fileapi:<src>` with the injected TTL. **`Cache` is a required argument of `NewFileAPIResolver`** (`ErrCacheRequired`) because upload reuse is that resolver's entire reason to exist — a caller who doesn't want a cache wants `FetchResolver` instead. (`DeleteFile` and the `{URI, Name}` cache entry it required were removed in v1.13 — no consumer ever called it; use `gemini.Client.DeleteFile` directly if cleanup is ever needed.)
- **`imgutil.MIMETypeByPath` returns `""` for unrecognized extensions**, and `fileAttachment` omits `MIMEType` in that case. Do not reintroduce an `image/jpeg` fallback — declaring the wrong type is worse than letting the server sniff the content. Query strings are stripped before extension matching (signed URLs used to defeat the guess entirely).
- **The MIME pair is named after the stdlib functions it replaces**: `imgutil.MIMETypeByPath` / `ExtensionByMIMEType` mirror `mime.TypeByExtension` / `mime.ExtensionsByType`, which this package exists to replace with a fixed table (the stdlib pair reads the OS MIME database, so its answers vary by machine). `ByPath` rather than `ByExtension` because the input is a path or URI — stripping the query string is the whole reason the function takes one. Keep the two names symmetric if either is ever changed.
- **`imgutil.ExtensionByMIMEType` is the inverse table and *does* default (to `.png`)** — that asymmetry is deliberate, not an oversight of the rule above. A declared MIME type decides how the receiver interprets the bytes, so a wrong one corrupts the content; an extension only shows up in the storage path, and the served `Content-Type` is set separately from `MimeType`. Refusing to name a file is worse than naming it `.png`. The two directions live in the same file and `TestMIMETypeAndExtensionRoundTrip` fails if a format is added to only one. It exists because go-comic-kit, go-veo-orchestrator and ap-comp each had their own copy of this switch, and ap-comp's had silently drifted (no `image/gif`, no case/parameter normalization) — the extension is baked into GCS object paths that the ap-* history keeps.
- **`gs://` detection is local** (`source.go: isGCSURI`, unexported because a URI-scheme predicate isn't this kit's concern). It was a forwarder to `go-utils/urlpath.IsGCSURI` until that package was removed; the successor is `go-remote-io/remoteio.IsGCSURI`, but depending on go-remote-io drags the GCS and AWS SDKs into the module graph for one `strings.HasPrefix`. Keep it lowercasing, so `GS://` counts: callers validate their own input with `remoteio.IsGCSURI`, which is case-sensitive, and this kit must stay the *more permissive* side. Making it stricter than the caller produces "the form accepted it but generation rejected it".
- **`ensureUploaded` is singleflighted** and its shared run is detached from the caller's context (`context.WithoutCancel` + `UploadTimeout`). The cache is only written *after* a successful upload, so without this, concurrent uses of the same reference each upload a duplicate; and without the detach, the first caller canceling would kill the upload every piggybacked caller is waiting on. `ports.ImageCacher` implementations must therefore be safe for concurrent use.
- **`CacheTTL` is deliberately not defaulted.** 0 is a meaningful value to the cache the consumers actually use: `ttlcache.DefaultTTL` *is* 0, meaning "use the TTL configured on the cache", so substituting a kit default would override the caller's configuration. `CompressionQuality`, `UploadTimeout`, `FetchTimeout`, and `MaxReferenceBytes` are defaulted because the resolvers themselves consume them and has nobody to defer to. `TestCacheTTLIsPassedThroughUnchanged` pins this. Watch the other end too: a cache whose default outlives the File API's server-side retention will keep handing back dead `files/...` URIs.
- **Inline fetches are bounded** (`source.go: sourceFetcher.readAll`): `FetchTimeout` (default 1m) caps one fetch, `MaxReferenceBytes` (default 32 MiB) caps the bytes read — an unbounded `io.ReadAll` of a remote URL is a memory and latency hazard. `sourceFetcher` is shared by both fetching resolvers so neither can quietly lose a bound.
- **File layout**: files are named for what they hold, not for their layer. `generator.go` (type/constructor/entry points/guard options), `reference.go` (collecting many references concurrently), `request.go` (prompt/options/seed), `executor.go` (model call + response parsing), `resolver.go` (chain + GCS + fetch resolvers), `resolver_fileapi.go` (upload + cache), `source.go` (transport, MIME sniffing, compression policy). There are no `*_helper.go` files — they turn into dumping grounds. **The resolvers deliberately stay in `generator` rather than getting their own package**: the split would buy nothing (same module, so `go.mod` is unchanged) while forcing `sourceFetcher`, `compression`, `fileAttachment` and the sentinel errors to be exported or duplicated.
- **Backend-specific option defaults** (`request.go: toOptions`): `ports.GenerationOptions` embeds `gemini.GenerateOptions`, so `toOptions` only fills what the caller left unset — `SafetySettings` (per-backend threshold: `Off` for Gemini API, `BlockNone` for Vertex, which rejects `OFF`) and `PersonGeneration` (`AllowAll` on Vertex; always stripped on the Gemini API backend, which doesn't support it). Caller-provided values are respected — the kit no longer overwrites them.
- **`Generator` holds no call guards, and that is the settled answer.** `WithRateLimit` / `WithRequestTimeout` / `WithMaxConcurrency` / `GenerateBatch` / `ports.BatchImageGenerator` all shipped in v1.13 and were all removed again, because every consumer independently rejected them:
  - **Rate limit + timeout + dedup belong to the workflow, not the kit.** Quota is per *project*, not per operation kind, so guarding image generation while text generation runs free protects nothing. All three consumers wrap `ports.ImageGenerator` in a `callguard.Do` decorator sharing one `*callguard.Guard` with their text generator, and call `generator.New(client, resolver)` with **zero options** (go-comic-kit `workflow/singleflight.go`, go-veo-orchestrator ditto — the latter pins the reasoning in `TestGuardCoversTextGenerationToo`). Keeping the kit's own limiter would only add a second place to configure one: set both to 30s and the effective interval is 60s, undiagnosably.
  - **Batching's unit was wrong.** go-comic-kit batches over a generic `render func(ctx, index) (T, error)` (`internal/operations/batch.go`) whose work item is "generate + write to GCS + update state", so a batch of bare `ImageRequest`s sits a layer too low to replace it and the caller wraps its own errgroup anyway.
  - **Don't route File API uploads through a shared `Guard` either** if guards ever come back. An upload is not a generation call and consumes no generation quota; putting it behind `WithRateInterval` makes every reference image burn a generation firing slot (5 references at a 30s interval = 2.5 minutes of waiting before the generation that needs them starts). `FileAPIResolverConfig.UploadTimeout` bounds uploads instead, and `uploadOnce` keeps its own singleflight — deliberately *not* `callguard.Do`, whose central feature would have to be switched off to use it here.
- **Ordering inside `Generate`**: `prepare` (validation + prompt build + auto-seed, no I/O) runs **before** `collectImageAttachments`, so a request that won't be sent never pays for fetching or uploading its reference images (`TestGenerateValidatesBeforeResolvingReferences` pins it, and fails if the two are swapped). Cancellation follows the caller's context alone.
- **Compression strategy**: when a resolver is constructed with `Compress: true`, PNG/GIF inputs are re-encoded as JPEG (quality from its `CompressionQuality`, defaulting to 75) — both inline parts and File API uploads are fully decoded/re-encoded in memory before being sent (no streaming compression). Non-compressible formats skip decode/re-encode entirely — the fetched `bufio.Reader` is handed straight to `FileManager.UploadFile` (which buffers it itself, to be able to retry).
- **Negative prompts** are not an API field; `buildFinalPrompt` concatenates them into the prompt text with a `[Negative Prompt]` separator. (Downstream prompt code — e.g. ap-story's design prompts — depends on this exact rendering; treat the separator as a compatibility contract.)
- **Reference images are resolved concurrently** (`reference.go: collectImageAttachments`), because fusion requests can pay one GCS/HTTP round trip per reference (depending on the resolver). Order is preserved (it affects how the model reads the references), a single reference skips the goroutines entirely, and the reported failure is the *first by input index* — with `context.Canceled` deselected, since one failure cancels the rest and would otherwise mask the real cause.
- **`ImageResponse.UsedSeed` is the requested seed, not one the API reports back** — the API never returns it. **Auto-seeding is the default since v1.13**: with no `Seed` in the request the kit picks one before sending, so `UsedSeed` is always a truthful reproducibility record (it used to be opt-in via `WithAutoSeed`, and the consumers that forgot it recorded a useless 0). `WithoutAutoSeed()` restores the old behavior for callers that manage seeds themselves. Seeds are bounded to int32 because `go-gemini-client` rejects anything wider (`ErrInvalidSeed`).
- **`ImageResponse` carries `Model`, `Prompt`, and `Usage`** alongside the bytes, so consumers can record cost and provenance without re-deriving them from the request.

## Conventions

- Comments are largely Japanese; sentinel errors are English with an `imagekit:` prefix — match the surrounding file.
- Tests use testify + hand-written mocks in `generator/mocks_test.go`: `fakeClient` records what was sent to the model (and injects failures/delays via its `generate` hook), `stubResolver` fakes reference resolution, and `newStubGenerator` wires both. Nothing touches the network.
- README.md documents the public API and quick-start wiring (memory cache, downloader examples) — update it when `ports` types or constructor signatures change.

## genai SDK boundary

This kit's public API deliberately contains no `google.golang.org/genai` types — the SDK stays inside `go-gemini-client`.

- Reference images travel as `gemini.Attachment`: inline bytes (`Data` + required `MIMEType`) or a URI reference (`URI` + optional `MIMEType`). `fileAttachment` builds the URI form for both GCS (`gs://`, Vertex only) and File API (`files/...`) sources — `GCSResolver` and `FileAPIResolver` return it; `FetchResolver` returns the inline form after downloading.
- `executeRequest` takes the prompt and attachments separately and calls `gemini.Generator.GenerateWithAttachments`, which places the prompt before the attachments. That ordering was measured against the previous images-then-prompt shape on a real cover-art prompt: the difference was within run-to-run variance, so no ordering knob was added.
- `parseToResponse` reads `Response.Attachments` (MIME type + bytes). Empty/blocked responses are already turned into errors by `go-gemini-client`, so this kit only distinguishes "no image data".
